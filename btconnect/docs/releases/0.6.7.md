# BTConnect 0.6.7 — 2026-10-23 Pacific

## Problem and behavior

An eBay createOffer HTTP 400/25702 rejection left `offer_attempted` set without retaining the typed response. Later guard errors overwrote the useful message, stranding an unchanged approved listing even when its inventory item was readable.

Creation attempts now retain request time and typed failure history. A confirmed 400/25702 rejection can receive one explicit recovery authorization through the existing `approve_listing_draft` tool. Authorization performs no eBay writes. It requires the exact approved revision, a five-minute settling period, matching original-photo hashes, unchanged inventory and policies, a complete active-listing scan and two empty SKU offer lookups. Execution repeats the checks and consumes the authorization before the request. New uncertain responses, malformed responses and cancelled requests remain read-back-only.

Pre-0.6.7 jobs lack a typed createOffer journal. An operator who retained the actual original HTTP 400/25702 response may import an attestation through `owner_approval_evidence` JSON:

```json
{"action":"retry_rejected_offer_creation_once","owner_approval":"Exact owner authorization and revision reference","rejection":{"http_status":400,"codes":["25702"],"source":"Reference to the actual original createOffer response"}}
```

This is explicitly recorded as operator-attested evidence, never represented as a stored provider response. Generic approval, absence alone, a timeout, or an unknown response is insufficient. Attestation cannot override a new typed or interrupted attempt. A consumed retry cannot be authorized again. An existing matching offer is reconciled instead of recreated. No automatic batch rejection retry policy is expanded.

## Validation and release

Synthetic regression tests cover the reproduced rejection, legacy evidence import, unchanged approval/originals, lost-response reconciliation, concurrent offer appearance, stale/expired authorization, changed inventory, duplicates, unknown outcomes and single-use retry behavior. Full suite and exact-head CI results are recorded in the PR and public recovery issue.

Deploy through the existing canonical GitHub integration. No schema or data migration, dependency, credential, marketplace permission or approval revision changes. Version 0.6.6 can still read the additive journal fields but cannot use the new recovery authorization; retain the journal when rolling back. Deployment itself does not publish inventory. Resume only a previously reviewed and approved listing, with a separately recorded recovery authorization.
