# 0.3.12 — Native batch photo mapping

## Failure and scope

Regular Chat successfully discovered the native tools after the connector refresh, but its two-photo batch failed the 0.3.11 exact file-ID mapping check before any download. That contract required Chat to duplicate an attachment reference in ordinary metadata and expected it to equal the host-resolved file ID. Native single-photo tests in the same regular Chat then stored both existing attachments successfully. Returned IDs used the `sediment://file_...` form. Their stored byte sizes and SHA-256 values matched the independently verified originals:

| Photo | Bytes | SHA-256 |
| --- | ---: | --- |
| Front IMG_0974 | 736367 | 87c76fbad5d62ba2f3c4bd849c43128754ff0955424e12004c7409c253a43056 |
| Back IMG_0975 | 716472 | 29eca80179d5b5a35ed873825945b7ee6da3c126ea91ba067d0a7934ab5ff8c3 |

The single-photo calls reported `storage_sha256_verified: true` and `source_sha256_verified: false` because they did not supply independent source hashes. The comparison above was made separately against already verified original hashes. No listing was created, approved or published. The existing private encrypted persistent store does not need replacement for this failure.

## Contract repair

Use the host attachment references in `files`. For each photo, set `photo_inputs[].file_index` to its **zero-based position in that files array**, plus its visually identified `role`. Do not set `file_id` when using `file_index`. Optional independent SHA-256 and byte size are still enforced.

For `files: [front_attachment, back_attachment]`, the metadata is:

```json
{"photo_inputs": [{"file_index": 0, "role": "front"}, {"file_index": 1, "role": "back"}]}
```

This explicitly maps already identified photos; upload order does not establish which physical item or side a photo depicts. Every file must have exactly one metadata entry. Repeated host files, missing entries, duplicate indexes, out-of-range indexes, and conflicting index/ID selectors fail before network or storage operations. Legacy exact `file_id` callers remain supported; mismatches are never silently remapped, normalized or guessed.

Results retain metadata order and include `file_index`, actual host `file_id`, role and verified persistent `photo` reference. Downloads still share one client with at most three active transfers and a ten-photo/12 MB-per-photo limit. Retain successful references and retry only failed photos, renumbering indexes for the retry's own `files` array. Content-addressed storage makes retries idempotent.

## Validation and rollout

320 regression tests pass, including ten new cases covering resolved-ID differences and invalid positional mappings. Tests exercise out-of-order inputs, correct role/hash binding, partial retries, private signed URLs, scope/revocation checks, and durable read-back. The full MCP path using index mapping saves separate drafts, requires exact owner approval, publishes through a simulated eBay service, verifies a simulated item ID and receipt, and does not duplicate publication on retry.

Deploy through the existing repository/Railway service, then refresh the existing ChatGPT connector tool schema. Verify one native two-photo batch from the existing regular Chat attachments using indexes, ideally with the independently verified hashes above. At the time of this commit, native single-photo production transfer is confirmed; production batch acceptance after deployment is pending. Real listing publication remains outside this storage-only test and requires explicit approval of a new saved listing.

No new storage provider, database migration, permission scope, listing revision format or publication authorization rule is introduced. Native file parameters continue to follow the [official file input contract](https://developers.openai.com/plugins/reference#file-apis).
