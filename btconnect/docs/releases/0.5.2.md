# 0.5.2 candidate — responsive preparation and faster policy readiness

Build impact: BTConnect only. Production remains 0.5.1 until the owner approves
this release. No new service, subscription, API key, dependency, configuration,
index or durable record-format change.

Fresh stored-photo reads still blocked the server request loop during preparation,
ordinary draft saving, validation and private retrieval. These paths now share the
same single-capacity worker as ingestion. Private retrieval includes base64 encoding
inside that worker. Original bytes, seller binding, checksum checks, encryption and
existing durability are preserved. No cross-request byte or validation cache.

Preparation retains both checks: one before upstream policy/duplicate reads, and
another before a new or revised draft is saved. The save still takes the seller lock
and atomically validates revisions and uniqueness reservations. The seller's grant
is rechecked inside that commit transaction, after any queue wait or photo processing.
Synchronous internal `ListingStore.save` callers retain the optional grant argument;
both hosted worker save paths always supply it.

Cancellation drains the worker before releasing its slot or the outer batch lock.
If a save finishes after cancellation was requested, its durable draft may exist
before the batch marks that item ready. Resume revalidates the originals and adopts
the same unchanged draft. Queued cancelled work never starts. The 35-second budget
includes queue time, but draining already-running work can exceed the deadline; Python
cannot safely interrupt that thread. This is bounded request work, not a background job.

The direct condition-recovery path, approval and publication retain their existing
synchronous checks and journal logic. No marketplace write becomes concurrent or
automatically retried. Large concurrent request/response buffers remain outside the
worker's capacity bound. No global memory or latency limit is promised.

See [five-draft measurements, raw samples and limitations](../benchmarks/2026-10-17-connect-preparation.md).
Five repeated large-photo runs reduce median maximum event-loop delay from 688 to
32 ms and backend elapsed from 1.16 to 0.97 seconds. Small-photo batches take about
8 ms longer; large-photo sampled peak process memory rises about 29 MiB. These are local measurements.
The tool description now accurately reports the existing 20-attempt preparation limit.
The tool names, input contracts and output shapes are otherwise unchanged.

Policy readiness now overlaps four independent business-policy/location GETs,
then the optional category and campaign reads (at most three in flight). Required
errors drain before propagating; optional errors retain their `unavailable` shape.
Cancellation drains both groups. Every request rechecks its grant and scope;
campaign pagination stays sequential and nothing is cached or automatically retried.
The successful path makes the same seven GETs. Under a controlled 50 ms delay per
GET, median readiness falls from 309 to 106 ms; three campaign pages fall from
412 to 209 ms. The zero-latency control is essentially unchanged. Readiness is a
discovery step, not a measured full-listing speedup. Up to four required reads can
already be running on failure, versus the old sequential early exit. See
[measurements and failure tradeoffs](../benchmarks/2026-10-17-connect-policy-readiness.md).

Verification: all 516 tests pass locally, plus compilation and an offline wheel
build. Ten new readiness cases exercise overlap, freshness, failures, cancellation,
revocation and pagination. Two existing framework deprecation warnings remain.
