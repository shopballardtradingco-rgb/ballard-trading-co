# 0.5.1 candidate — faster hosted reads and draft preparation

Build impact: BTConnect only. The owner requested performance work while new-photo
acceptance is deferred. This release requires no new service, subscription, API key
or configuration change. It creates two non-unique indexes in the existing database
at startup; no record conversion or separate migration procedure is required.

Ordinary record reads previously acquired SQLite's writer lock and scanned expired
records. Full batch reviews repeated that work for the batch and every item. They
now use read-only access and one consistent snapshot for the complete review.
Expiry is still checked before returning data; secure cleanup stays in real write
transactions. Token consumption, revocation and listing approval retain their
existing atomicity and freshness.

Fresh policy validation overlaps three independent policy GETs and two independent
category GETs. It retains every check and the same six-request total. Failures drain
the group before returning, cancellation stops children, and no paid call or
marketplace write is retried or parallelized.

One eBay HTTP pool now belongs to the ASGI worker lifecycle. OAuth, reporting,
Trading and Sell calls share connections, capped at eight with a 15-second idle
expiry. Credentials remain request-local, cookies are rejected, redirects remain
disabled and existing 20/30/45-second operation timeouts are preserved. MCP sessions
drain before the pool closes. Original downloads and optional AI remain separate.

Expiry cleanup uses a range index instead of scanning permanent records on each
write. Draft pagination uses an index on seller and draft ID instead of scanning
and sorting all uniqueness reservations. Existing constraints remain in force.

Five repeated offline measurements against deployed 0.5.0 show five fresh drafts
prepared in 167.5 ms versus 319.5 ms with a fixed 50 ms mock HTTP delay. A 25-item
review at 10,000 unrelated encrypted records fell from 32.74 to 2.88 ms, using one
database connection instead of 26. These are controlled backend measurements;
live eBay, ChatGPT latency and owner-time improvements are not measured. See
[full results and reproduction](../benchmarks/2026-10-16-connect-performance.md).

The additional pass compares against the first candidate: at 10,000 saved drafts,
journal writes fell from 1.239 to 0.209 ms and a 20-draft page from 23.09 to 0.480 ms.
Twenty local TLS reads used one connection instead of 20; the 18-page active scan
used four instead of 18. These are local measurements, not live speed claims. See
[resource measurements and limitations](../benchmarks/2026-10-16-connect-resources.md).

Original-photo ingestion now uses one bounded thread worker per application, covering
native single/batch ingestion and the existing raw upload route. Cancellation waits
for an already-running write to finish before returning or releasing capacity. Queued
cancelled work never starts, and a revoked grant prevents a later photo commit.
Original bytes and independent durable read-back remain intact. AnyIO was already
locked/installed; its cancellation API is now an explicit package dependency.

Preparation defaults to at most 20 items per call with the existing 35-second budget.
Every attempted item remains durable before execution yields. Redundant final batch
saves are removed and unresolved bookkeeping is saved together. No durable record
format changes. The 100-ready fixture uses five preparation calls instead of 20 and
takes 471 versus 711 ms; a 12MP ingest reduces measured event-loop delay from 233 to
23 ms. Sampled peak process memory increases from 196 to 206 MiB. See
[workload measurements](../benchmarks/2026-10-16-connect-workloads.md).

Release review additionally frees decoded image buffers before encryption, including
failed decodes. Against the previous candidate in fresh-process tests, maximum kernel
process RSS falls from 181.19 to 145.08 MiB for a 12MP JPEG and from 247.12 to 219.45 MiB
for a 40MP JPEG. Median ingestion is about 6–7 ms slower, with higher event-loop delay;
this is a memory tradeoff, not a speed gain. The different process histories mean these
figures should not be combined with earlier RSS measurements. See the
[method, raw samples and limitations](../benchmarks/2026-10-16-connect-photo-memory.md).

Validation: 497 regression tests pass. GitHub build/compilation results are recorded
in the PR. Existing originals, exact SKUs, prices, locations, approval revisions,
duplicate checks and publication journals remain unchanged. Production 0.5.0 stays
in place until this performance release is explicitly approved for deployment.

Rollback after an approved release: redeploy prior commit
`3ed24729b82b343d8eb7edc158af7dede086b78d`, preserving `/data`, keys, OAuth grants and
all saved records. No data conversion is required. Inspect any in-flight publication
journal before retrying work after a restart. The older release safely ignores the
additional indexes; do not remove records, keys or indexes during rollback. First
startup briefly takes a database write lock to build the indexes (2.82 MiB extra
in the 10,000-draft benchmark); deploy during an idle listing window.
