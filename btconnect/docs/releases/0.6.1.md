# BTConnect 0.6.1 listing readiness

The readiness tool advertised a photo quota without measuring its remaining
capacity. A bulk session could pass readiness and fail midway through upload.
It also described only manual promotion and incorrectly said card contracts
were absent, although both automatic promotion and card contracts already exist.

## Change

The existing authenticated readiness response now includes a photo_capacity
snapshot: encrypted bytes used (including unindexed files), quota remaining,
free disk, the independent 50 MB disk reserve, and the smaller of quota and disk
headroom. A failed measurement returns unavailable with null capacity, never an
optimistic zero-use estimate. Filesystem paths are omitted. Measurement uses the
existing bounded photo worker, keeping file traversal off the event loop.

No quota increase, new storage backend, migration, provider call, campaign
change, listing approval or publication is part of this repair. Upload limits
are still checked at write time; readiness does not reserve capacity. The
300,000,000-byte ceiling applies to encrypted bytes, not source file sizes.

## Verification

Five new regressions cover encrypted rather than original sizes, unindexed
files, duplicate ingestion, disk reserve, over-quota existing files, redacted
measurement failure and authenticated read-only access. Run the full connector
suite plus the existing Core exporter integration before deployment.

Live acceptance requires version 0.6.1, a measured photo_capacity response and
unchanged saved-work catalogs. A new-photo check and publication remain pending
the next owner-started session. Keep the persistent volume, keys and journal;
rollback is source-only to 0.6.0 without changing stored records.
