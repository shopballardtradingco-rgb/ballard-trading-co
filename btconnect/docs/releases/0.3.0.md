# Connector 0.3.0 — secure originals and approval-bound publication

## Scope

Extends the existing OAuth/MCP connector; no replacement service or new infrastructure. The prior `346b676` draft module landed, but had no draft tests and rejected ordinary photo references because of an escaped-dot regex. This release replaces that incomplete contract with a complete, revision-hashed draft and adds the missing workflow and tests.

- Original JPEG/PNG ingestion through expiring, single-use upload tickets. Validate bytes, dimensions, size and caller-supplied SHA-256; encrypt the unchanged original on the existing persistent volume. Stable seller-bound object references have no public download endpoint.
- Encrypted drafts, exact-revision approval records, physical-item/SKU/photo uniqueness reservations and durable publication journals.
- Separate `btco:listings` consent. Existing `btco:read` connections retain their previous permissions; refresh cannot escalate scopes. Listing consent requests `sell.inventory`, `sell.account.readonly` and `sell.marketing` in addition to existing read scopes.
- Original multipart Media API upload, inventory item and offer creation, approval rechecks, business-policy fingerprints, duplicate checks, publish and live item ID/URL verification. Existing inventory SKUs are never overwritten.
- Fixed 5% promotion in a reviewed existing US CPS campaign. Dynamic/CPC campaigns are rejected. An unsupported listing requires an explicit recorded eligibility reason in the approved draft. No campaign or budget creation.
- Buyer-paid domestic flat-rate policies plus explicit combined-shipping evidence. Calculated shipping is blocked until measured package data is implemented.
- Publication receipt retains the exact master SKU separately from the eBay-only alias and physical item ID. Vault reconciliation is explicitly pending until its own verified write completes.

## Safety and recovery

`BTCO_PUBLICATION_ENABLED` defaults to false. Do not enable it before owner consent, restored exact pilot text, original photo mapping, identity/condition review, policies, promotion eligibility, duplicate review and an approved complete revision are ready. Deploying code does not approve any listing or upgrade any grant.

All material fields, including photo checksums and selected policy/campaign fingerprints, bind approval. Edits clear approval; CDP master reassignment is rejected. Once publication starts, changes are blocked until its outcome is resolved. A per-seller OS lock serializes publication across processes on this volume. Each irreversible write records intent before making the request. After a timeout/restart, recover the same exact offer by reading eBay. Never automatically repeat uncertain creation or publication; an unresolved intent is an operator-review state, not permission to create another offer.

An error after eBay publishes may mean a live listing already exists. Inspect `job.offer_id`, `job.listing_id` and `job.phase`, then retry the same draft/revision for read-back recovery. Do not delete the draft, journal or uniqueness claims. Late active-feed visibility and lost successful responses are covered by tests. A completed retry returns the original receipt with its verification timestamp; it is not a new current-status census.

## Storage and operation

Keep the existing `TOKEN_ENCRYPTION_KEY`, database and `/data` volume. Encrypted photo quota is 150 MB on the existing 500 MB volume, maximum original 12 MB. Quota includes encryption overhead and reserves 50 MB free disk space. This fits a pilot, not hundreds of photo pairs. A durable private object bucket and lifecycle policy need a separately approved storage expense before scale-up. No original images, secrets, inventory exports or generated bundles belong in GitHub.

Back up the encrypted database and object directory together with a protected copy of the key. OAuth revocation deletes grants/tickets, while listing history and originals remain for audit/duplicate prevention. Retention/deletion tooling and a backup/restore drill remain pending. Keep one service/volume and one replica; distributed locking is not implemented.

## Verification

103 synthetic tests pass on Python 3.12; bytecode compilation and wheel build pass. Tests cover original-byte encryption/upload, single-use/revoked/expired tickets, old-grant write denial, OAuth scope escalation, whole-dollar prices, approval invalidation, nested material changes, literal CDP SKU preservation, seller isolation, duplicate claims, durable locks, foreign SKU protection, policy mismatch, lost inventory/offer/publish responses, delayed live-feed visibility and fixed-promotion recovery. A GitHub Actions workflow runs tests and packaging for every push/PR. Two upstream test-framework deprecation warnings remain.

Live Sell/Media/Marketing acceptance remains blocked by new owner-consented account permissions. No live eBay writes, new paid services or inventory changes were performed during this release. The five pilot listings were not published; their ten original photos were recovered, but exact approved description text was not retrievable. The approval list alone cannot substitute for that content.

## Remaining workflow work

An owner-facing batch review surface, original-photo retrieval for secure review, measured shipping, verified sold-comp sourcing, automated comic identification/text proposals, and a receipt-to-Vault reconciliation adapter remain future work. Current drafts require source-evidenced reviewed identity and condition. Active asking prices are never represented as sold comps. Live item IDs and URLs can only be returned after an actual successful publication and read-back.

## Rollback

Set the publication gate false before rolling code back. Retain the current encrypted database, photo objects and key; do not restore an older journal over a newer eBay outcome. Existing read-only OAuth grants remain compatible. Reconcile any in-flight offer before re-enabling writes. Railway deployment/CI evidence belongs in the canonical OS release record once observed.
