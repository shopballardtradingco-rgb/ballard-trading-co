# 0.3.11 — Ordinary-conversation original-photo transfer

## Diagnosis

Production already had encrypted persistent photo storage, single-use raw upload tickets, and a native `openai/fileParams` tool. This Work chat's exposed connector catalog contains the older tool set: it omits native ingestion and draft-contract tools, although readiness advertises ingestion. Native ingestion also required callers to calculate a SHA-256 and size before downloading, an unnecessary dependency on a code runtime for ordinary chat attachments.

The current raw helper successfully transferred the original `IMG_1038.jpeg` (566,185 bytes), checksum `507da9b030a8990e3cc68275ff3e39f898ba2a6a91f0f1bc00203cc3331a2d1d`, to the existing seller-bound production store on October 13. This was storage only: no draft, approval or listing was created from that photograph. Do not infer which book or side it shows from this transfer probe.

## Repair

- Single native ingestion now needs only the host file reference and photo role. The connector calculates SHA-256 and exact size, saves unchanged JPEG/PNG bytes, reads back the encrypted persistent object, and checks its SHA-256 and bytes before reporting success.
- An independently computed `sha256_hex` and/or `size_bytes` can still be supplied. Mismatches are rejected. `storage_sha256_verified` proves downloaded bytes match stored bytes; `source_sha256_verified` is true only when the independent source checksum was supplied and matched. A storage hash does not establish that a host supplied the camera's original instead of a transformed copy.
- `ingest_original_photos` accepts up to ten top-level native file objects and an explicit `photo_inputs` mapping by `file_id`. Roles and optional checksum/size belong to that mapping. Duplicate/missing IDs fail before network access. Results retain input order and file ID even when downloads complete out of order.
- Downloads share one HTTP client with at most three active transfers. Each file remains limited to 12 MB, including streams without Content-Length. HTTPS host restrictions, no redirects, timeouts, private URL handling, scope checks and grant revocation checks remain in place.
- Batch failures return per-file results: retain successful references and retry only failed files. Content-addressed storage makes repeated originals idempotent. Raw upload now also reads durable bytes before acknowledging success.

No database migration, new storage service, account scope, credential change, listing schema/revision change, approval bypass or marketplace write is introduced.

## Minimal workflow

1. Pass actual host attachment references to `ingest_original_photos` with one mapping entry per file. Never invent a download URL, checksum or file ID. Do not send thumbnails, generated replacements or base64 in chat. If native tools are missing, refresh tool discovery for the **existing** BTCo connector; do not recreate its account or server.
2. Check `complete` and every result. Group returned `photo` references by the explicitly reviewed physical comic and save each complete draft with `save_listing_draft`. Never guess front/back assignments from upload order. The saved draft binds ordered photo references/checksums to its revision; existing cross-draft duplicate protection rejects reused copies.
3. Display the full saved listing and originals. Record the owner's explicit approval of that exact revision with `approve_listing_draft`.
4. Only with publication authorization, call `publish_approved_listing` for that saved revision. Require `publication_status.all_checks_verified` and the live item ID. An uncertain outcome must resume/read the same draft, never create a replacement listing.

For N originals, native batch ingestion uses ceil(N/10) connector calls instead of N ticket calls plus N external uploads. Draft save, owner approval and publication remain separate boundaries. If the host cannot provide native files, the existing Work raw helper remains a supported byte-preserving fallback.

## Acceptance boundaries

The Python 3.12 regression suite passes 310 tests (297 baseline plus 13 new cases); compile and wheel packaging checks pass. Two existing upstream test-framework deprecation warnings remain. Automated tests exercise actual MCP calls and the production download/storage/draft/approval/publication code with synthetic images and simulated upstream eBay responses. They cover absent client metadata, bounded streams, independent checksum/size failures, mismapped file IDs, permissions/revocation, partial retries, shared connection/concurrency limits, durable read-back failure, encrypted persistence, and rejection before owner approval. The full sequence ends in a verified **simulated** item ID and a signed receipt, and a repeated publish has one total upstream publication.

The production storage probe succeeded. Ordinary ChatGPT host file injection remains unverified because this session does not expose the native file tools; deployment alone does not refresh a previously scanned connector catalog. A new real eBay publication also remains untested for this release because the owner has not approved a new test listing. Do not report the simulated item ID as a live listing or republish historical comics.
