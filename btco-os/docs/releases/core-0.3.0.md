# BTCore 0.3.0 — card preparation from saved photos

Problem: bulk uploads stopped at untitled drafts, requiring the owner to enter every card manually.

This release adds a persistent server queue using the existing saved originals. Existing cards use Intake → Prepare cards; completed new card batches queue automatically. The provider returns suggested identity, conservative visible condition, listing text, and an explicitly labeled price basis with source links. Empty fields are filled, prior AI suggestions can be updated after corrections, and manual edits remain protected. Nothing creates stock, assigns a CDP master mapping, publishes a listing or changes an original.

The phone review page shows all cards, their photos and their missing requirements. The owner checks and approves selected cards together. Export uses the exact 29 columns of the supplied CDP inventory import template. New CORE SKUs stay literal, unknown acquisition cost stays blank, and B007/section 2 is split deterministically. Random persistent image links expose only currently approved card images; photo/details changes invalidate those links and approval. Re-export after corrections. Avoid duplicate CDP imports until its preview confirms how it handles existing SKUs.

Operational behavior: up to 500 cards per queue request, one server worker, four-minute interrupted-job lease, no automatic retries after uncertain provider failure, and billing/auth errors pause queued work. A $10 monthly AI allowance is persisted and uses a conservative $0.40 reservation per request. No extra database tables, grants or destructive migrations. Queues, results, approvals and usage are included in existing backups. Credentials are server-only, optionally transported as an AES-GCM envelope. Open workspace access remains the owner's current choice; anyone with its address can enqueue work within the allowance.

Validation: synthetic queue/replay, manual-edit race, missing-back block, approval invalidation, CSV formatting, externally retrievable JPEG, billing pause, source allowlist, credential redaction, and restart/interruption tests. Mobile upload → automatic preparation → review → CSV acceptance, plus existing intake/open-mode browser and core suites. A real OpenAI request using one saved card front returned structured identification with three source links; it did not write production drafts or publish anything. Full-batch identification accuracy and CDP live importer acceptance require review of the real results. PostgreSQL and Docker checks run in CI.

Deployment: feature/card-bulk-upload, dedicated Core development API only. Stage the new commit and server AI credential variables together. Keep the existing photo bucket and database. On first use, prepare the existing saved queue; no re-upload is necessary. This release has no autonomous external marketplace writes.
