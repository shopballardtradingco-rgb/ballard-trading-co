# BTCore 0.6.7 — Save selected cards without false conflicts

## Problem and authorized scope

Tim's selected-card save stopped with "Another device saved first" and five unsaved rows. The old guard rejected any workspace revision change, including unrelated background preparation or mirror observations. The screenshot proves a revision conflict; it does not establish which writer caused it.

This is a targeted repair to the authorized development listing workflow. No real listings are published by testing.

## Changes

- Only /api/listing-rows and /api/publication/selection may accept an older workspace revision. Both validate every selected card's full content fingerprint and current preparation, linked Vault price, stock and publication locks inside the existing serialized/row-locked transaction.
- Load and change the latest saved state, preserving all newer unrelated data. Increment from the current database revision, never the submitted older revision. Future revisions still fail.
- All-or-nothing validation and operation-ID replay remain intact. Concurrent changes to different cards can both save; competing changes to the same card have one winner. Publication approval, originals, master SKUs and independent channel prices remain unchanged.
- Other mutation endpoints still require an exact workspace revision. No automatic retry or changed-content overwrite is introduced.
- The server repair works with an already-open 0.6.6 page: the owner can retry without reloading or retyping pending edits. A real selected-card conflict still requires review, with the affected title identified.
- New UI code clears stale "Saving the selected cards" progress after an error. The generic revision message no longer claims another device was necessarily responsible.

## Verification and deployment

- API tests cover older revisions with unchanged selected cards, preservation of newer unrelated work and originals, operation replay, current stock/publication/preparation locks, selected-content atomic rejection, strict unrelated endpoints and concurrent disjoint/same-card writes.
- Mobile browser regressions cover a background revision change while bulk edits and same-page publish preparation are open, plus a real selected-card conflict retaining the form.
- Require exact-candidate independent-runtime (unit/API, disposable PostgreSQL, eight browser suites and Docker smoke), browser and vault checks. Verify Railway SUCCESS, exact commit, /healthz 0.6.7 and matching app assets before declaring live.
- Native iPhone/Safari acceptance remains with the owner. This release does not connect CollX posting or complete CDP parity.
