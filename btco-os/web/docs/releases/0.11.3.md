# Browser 0.11.3 — verified publication reconciliation

## Scope

Adds an owner-private `/api/publication-sync` preview/apply/status operation and an operator helper. Vault verifies Ed25519 evidence exported from the existing connector's persisted publication journal, using a server-pinned public key and seller. It never accepts a caller-selected signing key or workspace. This is an operator API; a batch listing-review screen remains future work.

## Data

Exact physical-record/CDP matches preserve literal master SKUs, physical quantities, costs, sales, original marketplace IDs and CollX prices. A new eBay-only publication creates a zero-stock review record without asserting ownership. Conflicting aliases, master records, graded/raw classification or existing listing links require review. Repeated receipts are inert. Immutable audit events retain signed evidence. Generic inventory saves cannot add or remove publication links; the dedicated operation uses existing revision checks, chunks and recovery snapshots. Daily eBay sync recognizes publication links without creating a second item. Newer or manually recorded prices are preserved.

## Verification

Seven new tests cover a Python-signed interoperability fixture in WebCrypto, tampering, seller/key mismatch, whole-dollar contracts, CDP/CollX/quantity preservation, raw/graded rejection, duplicate/retry behavior and real Worker/D1 concurrent writes and readback. Required gates: full browser tests, release fingerprints, typecheck and build. Production acceptance is recorded in the canonical root release record after deployment.

## Limitations

No production receipt has yet been applied; the approved pilots remain unpublished. Exact reviewed listing content and owner-completed eBay consent are still required. The connector's receipt says reconciliation was pending when issued; Vault's independent readback is authoritative for completion. A historical receipt is not a current live-listing census. The signing key is pinned through `BTCO_RECEIPT_PUBLIC_KEY`; rotation needs an explicit migration retaining verification of historical evidence. Owner-private Sites service access is required; this route is not suitable for public/multi-tenant deployment without additional authorization. Browser visual and native-device QA remain unverified.

## Rollback

Restore the prior Site version without changing D1. Keep signed receipt events and the pinned public key; do not erase a newer reconciliation or publication journal. A source rollback removes reconciliation/link protections, so prefer a forward fix and keep publication disabled until verified.
